# CR-028: writing embedded fonts - a docx carries the fonts it needs, and Word uses them

Status: IN PROGRESS. Phases 0 and 1 DONE 2026-10-02 (§5); phase 2 (subsetting) next. Proposed 2026-09-27 (Jason asked for the draft). Drafted with Claude Opus 5.5 while
measuring, for CR-020, what Word does with `w14:ligatures` on Arabic. That probe had to embed a
font by hand, and Word 365 then ignored it. Owner: Jason Harrop.

Scope: an API that embeds a font file in a docx the way Word does. That means the obfuscated
part, a `w:fontTable` entry Word will act on, the settings flag, and a licence check, with the
round trip proved by docx4j's existing read path and by Word. Later phases: subsetting, and
pptx. Not in scope: xlsx (Excel has no font embedding), the anonymiser (it removes embedded
fonts, correctly), and any change to how docx4j *uses* an embedded font for PDF output
(`FontTablePart.processEmbeddings`, which works: the font is read from the docx and registered).
"Works" does not mean "embeds in the PDF as Word does": docx4j writes more font data than Word,
because its `+noliga` twin is declared single-byte and FOP copies a single-byte TrueType font
whole (fop-core `PDFFactory.makeFontFile`, TrueType branch; no embedding-mode attribute reaches
it), where Word subsets to the glyphs used. Measured in CR-029 §9.4 (real2 200.7 MB against
Word's 50.9, fonts most of it; one document 982 KB of fonts, 183 KB with no twin, Word 264 KB)
and re-measured 2026-09-30 by the fork session ("Hello world" in Arimo: 8,451 bytes subset on
the CID declaration, 191,915 whole on the single-byte one). A font embedded by this CR goes
through the same twin, so it too is written whole whenever a Latin span takes it. The remedy is
CR-020's switch (the twin gives way to `-liga` on the CID declaration, which is subset, now that
the gsub-features gate has passed), not this CR. No schema change: `w:fontTable`, `w:font` and
`w:embedRegular` are bound already.

## 1. What docx4j does today

Reading is complete; writing is a fragment.

- **Read.** `FontTablePart.processEmbeddings(Mapper)` finds each `w:font`'s `w:embedRegular`,
  `w:embedBold`, `w:embedItalic` and `w:embedBoldItalic`. It follows the relationship to an
  `ObfuscatedFontPart` (or a plain `TrueTypeFontPart`, which some producers write) and
  de-obfuscates it with the `w:fontKey` (ECMA-376 Part 4 §2.8.1: XOR the first 32 bytes with
  the key's 16 bytes, reversed). It registers the result with the mapper, so PDF and HTML output
  use the document's own font. `FontsAnalysis` reports an embedded font as its own decision
  (`FontDecision`, "the document embeds it").
- **Write, partly.** `TrueTypeFontPart.obfuscate(fontKey)` exists (846c4f3ab), for one case:
  with `docx4j.fonts.embedded.obfuscate=true`, a plain TrueType part a producer such as Google
  Docs wrote is replaced by an obfuscated one when `processEmbeddings` runs. There is no way to
  put a font *into* a document: no key generation, no part and relationship, no `w:font` entry,
  no `w:embedTrueTypeFonts`.
- **pptx.** `FontDataPart` models `p:embeddedFontLst`'s `.fntdata` parts, for reading. Nothing
  writes them.
- **Licence data.** docx4j's repackaged FOP font loader (`OpenFont`) reads `OS/2.fsType`, but
  only tests for the value 2 (restricted); `PhysicalFonts` then skips such a font for PDF output.
  It reads the panose. It does not read `ulUnicodeRange1-4` or `ulCodePageRange1-2`, which are
  what Word's `w:sig` carries (§3).

## 2. Why

- **Probes.** The layout-fidelity probes are generated by `Corpus.java` with docx4j. A probe
  that needs a particular font, like `ligatures-arabic` (Noto Naskh Arabic, whose ligature
  lookups are known), cannot be generated today. It was built by a Python script
  (`~/fidelity-arabic-ligatures/make_probe.py`), outside the corpus generator. With this CR it
  moves into `Corpus.java`. More generally, Word and FOP could then be compared on the same font
  file rather than on two machines' font sets.
- **Generated documents that look the same everywhere.** A docx4j-generated report in a
  corporate or open-licence font opens in its own font on a machine that lacks it. Word does
  this for its own users with File > Options > Save > "Embed fonts in the file".
- **The MCP server and the Markdown pipeline** could offer "embed the fonts this document
  uses" as one call.

## 3. What Word needs: the measurement that shapes the design

The Arabic probe embedded Noto Naskh Arabic, obfuscated exactly as docx4j de-obfuscates. docx4j
reads it back byte for byte, and its re-save keeps the part, the key and the flag (checked
2026-09-27). **Word 365 did not use it.** It drew those rows in Times New Roman, and its
re-save dropped the embedding. The entry the probe gave the font was minimal:

    <w:font w:name="Noto Naskh Arabic"><w:charset w:val="00"/><w:family w:val="roman"/>
      <w:pitch w:val="variable"/><w:embedRegular r:id="rId1" w:fontKey="{...}"/></w:font>

Word's own entries for the fonts it embedded in the same re-save carry the panose and the
signature. Calibri, for example:

    <w:font w:name="Calibri"><w:panose1 w:val="020F0502020204030204"/><w:charset w:val="00"/>
      <w:family w:val="swiss"/><w:pitch w:val="variable"/>
      <w:sig w:usb0="E4002EFF" w:usb1="C000247B" w:usb2="00000009" w:usb3="00000000"
             w:csb0="000001FF" w:csb1="00000000"/>
      <w:embedRegular r:id="rId1" w:fontKey="{...}"/></w:font>

and Traditional Arabic has `w:charset w:val="B2"` (Arabic) with `csb0="00000041"`. So the
likely causes, to be measured and not assumed (phase 0):

1. **`w:sig` absent.** Word decides from the signature whether a font covers a script, and
   substitutes when it believes it does not; an Arabic run is exactly the case.
2. **`w:charset` 00 (ANSI)** for a font whose text here is Arabic.
3. Something about the part or the relationship that docx4j reads but Word does not: the part
   name, the content type (`application/vnd.openxmlformats-officedocument.obfuscatedFont`), or
   the relationship type.

A second observation from the same probe bears on the measurement design: Word drew the
Traditional Arabic and Arabic Typesetting rows in Calibri, although both fonts are installed on
the VM (Word's re-save embedded them). The probe's entries for those two had no `w:sig` either.
So cause 1 may govern installed fonts too, which would make the entry's fields matter for every
docx4j-written fontTable, embedded or not. Phase 0 separates the two cases.

**The oracle for the fields.** Word writes the entry for any font it embeds. So for a given
font file, docx4j's computed `w:panose1`, `w:charset`, `w:family`, `w:pitch` and `w:sig` can be
compared field by field with Word's own entry for the same file. A test can hold Word's values
for a few fonts, fixed.

## 4. Design

A new class in `org.docx4j.fonts`, `FontEmbedder`, used as:

    FontEmbedder.embed(wordMLPackage, new File("NotoNaskhArabic-Regular.ttf"));        // regular
    FontEmbedder.embed(wordMLPackage, boldFile, FontEmbedder.Style.BOLD);
    FontEmbedder.embed(wordMLPackage, file, "Noto Naskh Arabic", Style.REGULAR);     // name given

It does the following:

1. **Read the font** with docx4j's `OpenFont` (TrueType, and OpenType with TrueType outlines;
   the first face of a `.ttc`, with a warning). A CFF-flavoured OpenType font (`OTTO`) is
   refused: Word embeds TrueType outlines only. Phase 0 confirms that.
2. **The licence check**, from `OS/2.fsType`, which `OpenFont` is extended to keep whole:
   - bit 1 (restricted licence embedding) refuses, with an exception naming the font;
   - bit 9 (bitmap embedding only) refuses too;
   - bit 2 (preview and print) embeds, and logs that Word will open the document read-only;
   - bit 3 (editable) and 0 (installable) embed;
   - bit 8 (no subsetting) is recorded for phase 2.

   docx4j never overrides a refusal. The Javadoc says plainly that the font's licence, not the
   flag, is what the user answers to: the flag says only what the vendor permits by default.
3. **The part**: a fresh GUID as the `w:fontKey`, the obfuscation `TrueTypeFontPart` already
   implements (moved to a static helper both classes use), and an `ObfuscatedFontPart` at
   `/word/fonts/fontN.odttf` related from the font table part. The font table part is created
   if the package has none.
4. **The entry**: the `w:font` of that name is created or updated, with `w:panose1` (OS/2
   panose), `w:charset` (from the code page ranges, as Word derives it: phase 0 records the rule
   against Word's entries), `w:family` (from `OS/2.sFamilyClass`/panose), `w:pitch` (`post`
   `isFixedPitch`), `w:sig` (`usb0-3` = `ulUnicodeRange1-4`, `csb0-1` = `ulCodePageRange1-2`, as
   8-digit hex), and the `w:embedRegular` (or Bold/Italic/BoldItalic) with its key. An existing
   embedding of the same style is replaced, and its part removed.
5. **The flag**: `w:embedTrueTypeFonts` in the settings part. `w:saveSubsetFonts` only with
   phase 2, where the policy (§5 phase 2) decides it.

A second entry point fills in the fields of step 4 for fonts that are *not* embedded:
`FontTable.describe(wordMLPackage, fontName, file)`. That applies only if phase 0 shows Word
substituting installed fonts for want of a `w:sig` (§3).

2. **Subsetting** (`w:saveSubsetFonts`), from the characters the document uses, with
   docx4j's `TTFSubSetFile`. Word's own subsets keep the glyph count and ids (seen in its PDF
   subsets, 2026-09-27); whether its *embedded* subsets do is for phase 0 to say, and the
   subsetter follows. Refused where `fsType` bit 8 says no subsetting.

   **Word's rule, and the policy (decided 2026-10-02).** Word subsets only when the document's
   `w:saveSubsetFonts` is set (its option "Embed only the characters used in the document"),
   and then only a font of which fewer than 32 characters are used: at 32 or more it embeds
   the whole font (Microsoft, `Document.SaveSubsetFonts`, §9). With the setting off it always
   embeds the whole font. docx4j replicates that as the default, because the document is the
   oracle: a docx this CR writes is one Word would have written, and Word's first re-save
   applies the same rule, so the Office check can compare like with like. It is configurable,
   because docx4j's callers are not Word users and decide per call what Word decides per
   machine: an `EmbedPolicy` on `FontEmbedder` with three values, `AS_WORD` (the document's
   `w:saveSubsetFonts` plus the 32-character threshold; the default), `WHOLE` (always the
   whole font: a document someone will go on editing, since a subset cannot gain characters),
   and `SUBSET` (always the characters used: a document for distribution). Two constraints sit
   under all three: a subset keeps the glyph count and ids (unused outlines emptied, nothing
   renumbered, as Word's subsets do and as the obfuscated part's cmap requires), and the
   `fsType` check comes first, so a font whose bit 8 forbids subsetting is embedded whole or
   not at all whatever the policy asked. **Office check for this phase (Jason, 2026-10-02):** a docx
   whose embedded font is a docx4j subset for fewer than 32 characters (Word's own subsetting
   case) must open in Word with no repair prompt and draw from the subset, and Word's re-save
   of it is read for what Word keeps; phase 0's e5 (a subset of about 50 characters) drew, and
   e11 gives the shape Word's own subsets have. `AS_WORD` writes `w:saveSubsetFonts` as it found it;
   `SUBSET` sets it, `WHOLE` clears it, so the settings part says what the parts hold.
3. **pptx** `p:embeddedFontLst` (`FontDataPart`), if there is demand: PowerPoint's `.fntdata`
   format is to be measured first.

## 6. Risks

- **Licensing.** The main one. Mitigated by refusing what the font's flags refuse and by
  documenting that the flag is not the licence. Open-licence fonts (OFL, Apache) are the
  expected use.
- **Size.** A full CJK font is 10-20 MB; that is phase 2's reason.
- **Name clashes.** Word prefers an installed font of the same name to the embedded one. Phase
  0 records this; the API documents it.
- **Variable fonts.** Word's embedding of a variable font is untested. Phase 1 refuses one
  (`fvar` present) until measured.
- **Behaviour on other consumers.** LibreOffice reads embedded fonts; its needs may differ from
  Word's. It gets a row in the phase 1 check, as a note rather than a gate.

## 7. Hand-offs

No schema change, so objects-ts has nothing to regenerate. The python and core-ts ports read
fontTable but write no fonts; they get a note when phase 1 lands, in case either grows a
writer. The docx4j-mcp session gets the API when phase 1 lands.

## 8. Effort (rough)

Phase 0 is a day (probes plus reading Word's output). Phase 1 is two or three days. Phase 2 is
two days. Phase 3 is not estimated.
